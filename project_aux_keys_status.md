AUX/KEYS is a browser-based (Web Audio API + JS, no build step, targeting PWA) app that listens to a keyboard's audio signal and detects/plays back notes and chords, aimed at Pentecostal/contemporary worship keyboardists. Full vision is an arranger-keyboard (Yamaha PSR/Korg Pa/Genos-style): mirror mode, one-man-band auto-accompaniment, voice/style switching, registrations/setlists, auto-harmony, register split, chord-chart broadcast, etc. Canonical files: [[reference-aux-keys-files]].

**Why:** solo keyboardist in a live-worship setting wants the experience of a full band without other musicians present. Groove/harmonic vocabulary should be gospel/contemporary worship (shuffle grooves, triadic/7th progressions), explicitly not classical/orchestral/chant.

**Build phasing agreed with user** (roughly): Phase 0 capture+pitch refactor → Phase 1 chroma/chord detection → Phase 2 voice switching (Tone.js)/style selection/sustain/fills → Phase 3 auto-band (bass/drums/pads) → Phase 4 registrations/setlists/sync-start → Phase 5 chord-chart broadcast/session recording → Phase 6 key detection/auto-transpose/auto-harmony/register-split/dynamics/humanized timing → stretch: stab pads, vocal-mic ducking, learn-from-recording.

**Status as of 2026-08-24:**
- Phase 0 DONE and verified on real hardware: migrated pitch analysis from a `requestAnimationFrame`-driven main-thread loop to an `AudioWorklet` (`pitch-processor.js`), decided/resolved in favor of doing this *before* chord detection rather than waiting for the drum-scheduler stage, since chroma detection would otherwise need a second migration later. Same YIN algorithm, ring-buffered, hopped at 1024 samples (~43Hz) to stay inside the audio thread's timing budget.
- During Phase 0 verification, found and fixed a real bug (not a migration regression — pre-existing, previously unverified): the note-lock debounce only ever gated the synth **voice**, not the displayed note **letter**, so the display flickered at note boundaries even though the code comments implied it was protected. Fixed by driving the displayed letter off the locked `lastMidi` instead of the raw per-hop candidate. See [[feedback-stability-layer-must-gate-display]].
- Phase 1 chroma/chord detection: added as a parallel analyzer, deliberately kept on the **main thread** via the existing `AnalyserNode.getFloatFrequencyData()` (rAF cadence), not inside the AudioWorklet — chord state isn't timing-critical the way pitch→voice latency or future beat-locked drums are, and avoids hand-rolling an FFT inside the worklet (no external libs allowed, per project's no-build-step constraint). Cosine-similarity match against major/minor triad templates only for v1 (7ths deferred). Built the chord display with the lock-before-display pattern from day one, learning from the Phase 0 bug.
  - First real-hardware test came back "not registering" — the blind-guessed `CHROMA_SILENCE_ENERGY` threshold (0.5) was way too strict for this signal path (mic picking up keyboard through a speaker, same weak-signal situation that made the Phase 0 RMS gate need to go as low as 0.01). Added a live diagnostic readout (energy value / best-guess root+quality/confidence %, shown even before a lock commits) instead of guessing again, then lowered the energy floor to 0.02 — confirmed working after that change. **Lesson: for this input path, always add a live numeric readout before tuning any new energy/confidence threshold — don't guess a second time.**
  - Root+quality *correctness* (not just "displays something") not yet independently confirmed — tester isn't a musician, so verification is observational only (steady while held, changes on chord change, clears on release), same as the pitch protocol.
  - Second bug found during that same verification pass: mid-hold flicker — the display-lock mechanism worked, but a wrong candidate could genuinely win 4 consecutive frames by chance because the raw chroma vector itself was noisy (chord lock had no equivalent of the pitch detector's median-smoothing step, only the lock). Fixed with a 4-frame rolling average of the chroma vector before matching (`averageChroma`, mirrors the pitch detector's median-of-5 pattern) plus bumping `AnalyserNode.smoothingTimeConstant` to 0.85. Confirmed fixed via real-hardware retest — chord detection now holds steady. **Pattern for later:** any new lock/debounce needs *both* layers — smooth the raw signal AND require consecutive-frame agreement — one alone isn't enough; a lock without upstream smoothing just means noise takes longer (but still manages) to flip it.
  - Phase 1 now considered verified end-to-end (register, energy/confidence tuned to real mic-pickup levels, mid-hold stability confirmed).
- Mode switcher (Mirror / One-Man-Band) built as pure routing, per the original open question about getting this structurally right early. `lastMidi`/note-lock state tracks continuously in both modes (groundwork for register-split/auto-harmony later); only the actual voice-triggering calls (`startVoice`/`updateVoiceFreq`) are gated by `appMode`. Chord detection always runs regardless of mode. In Band mode the mirror voice is silenced and the UI says accompaniment isn't built yet (Phase 3) — honest placeholder, not a fake band sound. Not yet verified on real hardware — next step.
